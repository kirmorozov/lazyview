# Integration tests of the `integration tests` step of .github/workflows/ci.yml (the
# `--skip chaos_` run of `--test '*'` in every MySQL-family job) that may still fail without
# blocking a CI run: one "<test name> #<open issue>" per line, the shape of
# tests/chaos-known-red.txt. Blank lines and `#` comment lines are ignored; the name is the test
# exactly as cargo prints it, module path included (`pinned::…`, `definitions::…`).
#
# scripts/chaos-gate.sh reads this file in that step (--label "$FLAVOR integration"): a failure
# listed here passes the step and is written to the job summary with its issue, an unlisted one
# fails it with a ::error:: naming the file to fix. So this list is the only thing between a new
# integration regression and a red job. The test still RUNS and is reported: no continue-on-error,
# no skip, no retry anywhere, and with this file empty the step is strict exactly as it stands.
#
# EVERY ENTRY IS TEMPORARY AND OWNER-APPROVED (one owner decision per entry, never a bulk allowance)
# and the fix PR for its issue MUST delete the entry here: this file is not a place to park a
# failing test.
#
# `pinned::reg_cascade_refusal_seed_replay` entered this list on owner approval (2026-11-22) for the
# cascade-seed replay that kept main red since 0225453. It stays. PR #329 fixed the half of it that
# was the harness: the crash now runs at the engine's own caught-up point with a seeded window batch
# instead of at a wall-clock instant with whatever the writers had emitted, so a run can no longer be
# red because "the reproduction did not fire". What it is red for now is the other half, the engine's:
# after the crash replay the materialised view is still one row short of the oracle and stays short on
# the re-check (`oracle has 1195 rows, MV has 1194` on `mariadb123`, run `fix-m123/a4-015226Z`). That
# is a data-consistency failure and no tolerance is being asked for it: the PR that fixes the engine
# deletes this line.
