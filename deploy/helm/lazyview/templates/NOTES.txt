Two things to check now:

  1. The credentials Secret must exist and be readable, then start the pods:
       kubectl -n {{ .Release.Namespace }} get secret {{ .Values.secret.existingSecret }}
       kubectl -n {{ .Release.Namespace }} rollout status deployment/{{ include "lazyview.fullname" . }}
     The `setup` initContainer creates and migrates lazyview's own tables on every pod start, so a
     rollout with a new image is also the upgrade step.

  2. The logs of both runs, and what the instance is doing:
       kubectl -n {{ .Release.Namespace }} logs -l app.kubernetes.io/name={{ include "lazyview.name" . }} --prefix \
         | grep -E 'standing by|took over|streaming'

With more than one replica, every pod shares LAZYVIEW_INSTANCE_ID ({{ .Values.instanceId | quote }}):
one holds the named lock on the source and streams the binlog, the others are hot standbys. To run a
second, independent lazyview in the same namespace, install a second release with its own
instanceId — never edit the ConfigMap of this one.
